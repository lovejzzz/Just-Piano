# pass34：释放状态推进、声部交接与实际 PCM 分歧

本轮把上层释放节点的连续计算接到已验证的制音系数公式，并追查 pass33 的松键后音频差异。新增代码是独立计算和只读诊断工具；尚未接入网页音源，完整琴槌接触力、弦反馈与制音毡模型仍未验证。

## 本轮结果

| 实验 | 数值检查 | 实际音频 |
|---|---|---|
| 同一释放系数点六次独立运行 | 46 次更新、138 个系数分量逐位同 | 五次与原版基准 PCM 相同，一次不同 |
| 三次释放 setter 捕获 | 每次 52 条记录，合计 468 项检查同 | 三次基准 PCM 同 |
| 同次 setter→refresh→coefficients | 86 条记录、267 项交接/缓存检查同 | 基准 PCM 同 |
| 独立 refresh 捕获 | 26 条记录、25 项缓存检查同 | 基准 PCM 同 |
| 上层释放节点单断点连续轨迹 | 八步递推、24 项检查逐位同 | 基准 PCM 同 |
| 计算的释放轨迹→六次系数捕获 | 五次各 32/32；异常运行 20/24 | 保留四处失败及对应异常音频 |

前四项共有 11 次有效运行，全部确认被调试原生进程正常退出；局部算术与交接检查通过，PCM 为 10/11 相同。加上最后的上层轨迹捕获，共 12 次有效运行、11 次基准 PCM 相同。不能据此声称捕获总是无扰动，或完整音源已经匹配。

## 可执行的状态递推

`1005e1d18` 的活动释放分支在 `1005e1e94` 执行 float32 融合乘加：

```
candidate = fma32(dt, velocity, previousPosition)
intermediate = min(keyCap, max(0, candidate))
position = min(intermediate, softCap)
```

原指令分别保存 intermediate 和 position。实际短 A4 刺激中，内部 key_index=60（不能将它当 MIDI 音高），velocity=-98.6013412475586，dt=0.0013333333190530539，两个 cap 都为 1。连续输出为：

```
0.8685315251350403
0.7370630502700806
0.6055945754051208
0.4741261303424835
0.3426576852798462
0.21118922531604767
0.07972077280282974
0
```

[release-key-state.mjs](../dsp/release-key-state.mjs) 计算该分支。[捕获脚本](../scripts/pianoteq_capture_release_advance.py) 在一个固定硬件点观察相同节点的连续入口，下一次入口中的存储值作为前一步的实测结果；没有声称这是即时返回点观测。[重放脚本](../scripts/pianoteq_replay_release_advance.mjs) 只用首次捕获的位置初始化，之后始终传递自己的输出，不从每一步实测结果重置。

24 项包括八次输入连续性、八次位置、八次中间值。速度、dt 和两个 cap 仍为捕获输入；本轮没有恢复速度的生产公式，也没有覆盖其它按键、踏板和非单位 cap 分支。这是释放控制状态，不能直接命名为制音毡接触位移或接触力。

## 声部交接的具体内容

REA/Ghidra 和原指令确认 `100460110` 先调用 `10020df90` 消费上层挂起状态，再把 H+2ec8 及 H+2ec5/2ec6 交给 `1005337f0`，其中 V=H+168。普通分支从 `100460308` 和 `100460320` 连续调用两次相同 setter，不是两根不同琴弦。

setter 写入 V+8cc、V+924、V+925；在 release 非零、输入位置为 1、V+931 bit0 置位时另将位置清零。实际捕获验证了普通分支，未动态覆盖这一特殊清零分支。

`1006e4f5c` 根据 V+8cc 及缓存 V+8c8 等判断是否刷新系数。`1006e5344` 只出现在系数更新路径，不能把它缺少一次记录等同于少渲染一个音频块。

[交接捕获脚本](../scripts/pianoteq_capture_release_handoff.py) 支持 setter、refresh 和同进程 combined 三种模式；限定短刺激的计数窗口 3000..4608。combined 同次运行逐条对照 setter 输入/存储值、上层当前位置、刷新位置与上一块缓存。三次普通 setter 捕获每块确有两条相同写入。

## 异常运行没有被当作通过

六次系数捕获中的第三次只有六条更新，其余五次各八条。在 sample_counter=3712：

| 数值 | 正常轨迹预测 | 异常运行实测 |
|---|---|---|
| 释放位置 | 0.3426576852798462 | 0.07972077280282974 |
| duration | 0.8401896357536316 | 0.4822598993778229 |
| rate | 11.759705543518066 | 20.487672805786133 |
| gain | 4.437060832977295 | 6.211884498596191 |

若直接用该次实际位置代入系数公式，三个系数全都正确；若使用独立推进的正常位置，则四项失败。这将分歧收窄到释放状态/更新时序，但没有证明是哪个写入者或调度机制导致，也不能把跨运行对照当同次执行的因果证据。

异常 PCM 的 SHA-256 为 `db183923c929cfe84dd3833f15e812177961c975265c0d6787c5a7be1bcb44db`，不是 pass33 的 `19481a…` 变体。与基准 `1907f854…` 相比，第 4243 帧开始不同（48kHz，零起算），152875 个交错样本不同，最大差 22502 个 24-bit 整数单位，归一化 RMS 差 0.00012638944489430835。不能因另十次相同而丢弃它。

[审计脚本](../scripts/pianoteq_audit_release_runs.py) 分别报告局部检查、原生退出状态和 PCM 一致性。上述 11 次审计明确 `passed=false`、exit 1；异常轨迹桥接也 exit 1。对真实 setter 和连续递推记录分别故意改动一 ULP，两项负对照均被拒绝。

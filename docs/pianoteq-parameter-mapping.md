# Pianoteq 9 参数映射追踪

本记录针对已安装 9.2.5 ARM64 构建。已恢复一类实际归一化映射公式，并以 5 个公开控件共 15 个采样点验证；同时把音板五个传播参数追溯到上游模型对象字段。现已通过属性查找 switch 闭合「命名元数据 ID → 标量属性记录 → 映射对象 → 正向/反向公式」链路。标量属性到最终模型字段的 setter 链路仍未完整连接，尚未证明完整物理耦合。

## 内部元数据表的确切结构

`FUN_10067703c` 初始化 `0x145`（325）个、每个 `0x88` 字节的记录，总长度 `0xaca8`。末尾循环明确将循环索引写入每条记录 `+0`。记录中的字符串位于 `+0x08`、`+0x20`、`+0x38`、`+0x50`，初始化时部分名称会复制到两处，`+0x80` 另有标记值。该函数没有建立物理系数的浮点运算。

字符串常被编译成若干立即数写入栈，因此仅搜索明文名称会漏掉大部分条目。通过恢复这些字节，可以确定以下记录。这里的内部索引**不是** JSON-RPC 返回的 `index`。

## 音板配置偏移必须换算

已有音板报告中 `x19+0xc4` 等偏移，是相对 `FUN_100056f98` 的第二个参数。这个指针指向「结果容器 + 配置」的组合区域，并非 `FUN_100278cb0` 的配置起始地址。

具体数据流：`FUN_10037907c` 将输入配置复制到栈上的 `auStack_288`，随后传入 `&local_2a0` 给 dispatcher。后者在其 `+0x18` 处才是配置起始地址。dispatcher 汇编 `0x100056fc4` 也明确做 `x1=x19+0x18`。因此追踪原始配置字段的写入时，应使用下面右列。

| 传播器浮点参数 | dispatcher `x19` 相对偏移 | 原始配置相对偏移 | copy 函数 `undefined4*` 索引 |
|---|---:|---:|---:|
| `s0` | `0xc4` | `0xac` | `0x2b` |
| `s1` | `0x9c` | `0x84` | `0x21` |
| `s2` | `0xbc` | `0xa4` | `0x29` |
| `s3` | `0xc0` | `0xa8` | `0x2a` |
| `s4` | `0xa0` | `0x88` | `0x22` |
| `s5` | 固定浮点位模式 `0x3f9a362c` | 无 | 无 |

`FUN_100278cb0` 对这些字段做复制：其中若干浮点字段被合并为 8 字节读写。因此，即使反编译器显示 `undefined8`，也不意味着它们是整数参数或双精度浮点参数。该函数的容器复制和字段复制没有把 GUI 值转换成上述字段。

传播器内的算术作用见 [音板计算报告](pianoteq-dsp-findings.md)。仍不能把 `+0x84` 命名为 Impedance，或把 `+0xa4` 命名为 Q，直到上游实际写入链路成立。

## 第二轮：配置生产者已缩小到一个调用

`pass2-config-builder.json`（`ev_739a46aa5f796c32db8bbcaa0d6181805cb0ac60b8b34ec01082b1fbfe710a0a`）显示 `FUN_1003a8680` 在调用缓存之前：

2. `FUN_1001ba68c(..., &local_2a0, param_2, ...)` 填充配置。
3. `FUN_10037907c(..., &local_2a0, ...)` 请求音板响应。

因此下一个应追踪的实际系数生产函数是 `0x1001ba68c`，而不是继续分析复制构造函数。`FUN_1003a8680` 还将返回数据写入一组 `0x80` 字节记录的 `+0x74`，并设置 `+0x78/+0x7a` 标志。尚未识别这些记录的完整类型或音频消费者，不能据此将其称为实时耦合求解器。

### 数值标度注册与别名注册分开

`FUN_10061b224` 的 `pass2-registry-values.json`（证据 `ev_bed91495dda19a11339d9cd04a3639e852830482b37ce18bcd923511960eafff`）确实构造数值映射对象，调用 `FUN_100434810` 写入管理对象中步长 `0x58` 的记录。存在至少以下映射构造候选：`FUN_1003aa714`（四个浮点位模式输入）、`FUN_1000211d0`（三个）、`FUN_1006d7074` 和 `FUN_1003d5908`（两个）。本轮随后取得了第一种构造器及其正向、反向方法，确切公式见下节；其他映射类型不按参数形状直接命名。

## 已恢复并用公开接口验证的数值标度公式

本节进一步取得了映射对象的构造、正向求值、反向求值，已超出名称和函数结构证据。它证明的是**归一化控制值到显示/标量值的标度**，尚不等于这些标量到琴槌接触力、弦张力或制音器阻尼系数的完整映射。

定义构造器输入为最小值 `a`、中点值 `b`、最大值 `c` 和附加斜率输入 `d0`。`FUN_1003aa714` 实际计算：

```text
d = min(d0, 0.95 × (b − a))
p = log2((c − a − d) / (b − a − d/2))
若 |p − 1| < 10⁻⁵，则令 p = 1。
```

正向函数 `FUN_10095d0cc` 在 `p=1` 时返回 `a+(c−a)x`。非线性分支的式子为：

```text
y = a + (c − a − d) × xᵖ + d × x       （x ≥ 0）
y = a + d × x                           （x < 0）
```

反向函数 `FUN_1005d6a58` 同时提供独立交叉证据：它针对同一个幂项加线性项计算残差和导数，以 Newton 迭代求归一化值，夹到 `[0,1]`，最多约 100 次迭代；`p=1` 和 `d=0` 有直接反解分支。`FUN_100580a64` 验证 `f(0)=a`、`f(0.5)≈b`、`f(1)=c`。正向反编译输出遗漏了 `powf` 参数。汇编在 `0x10095d0cc` 将对象 `+0x18` 的指数载入 `s1`，保留输入 `s0=x`，在 `0x10095d138` 调用幂函数，随后两次 `fmadd` 完成上述方程。该汇编排除了把无参 `_powf()` 伪代码误当作完整调用的风险。

在 `NY Steinway D Mix` 上，通过公开 API 把对应参数设为归一化 `0.25 / 0.5 / 0.75`，读回显示值后，与构造器常数组合进行独立计算：

| 控件（静态查找分支确认） | 数值记录偏移 | `(a,b,c,d0)` | 公式预测三点 | API显示三点 |
|---|---:|---|---|---|
| Hammer Hardness Piano | `+0xb18` | `(0, .3, 2, .05)` | `.0513 / .3000 / .9024` | `.05 / .30 / .90` |
| Hammer Hardness Mezzo | `+0xb70` | `(0, .8, 2, .2)` | `.3222 / .8000 / 1.3663` | `.32 / .80 / 1.37` |
| String Length | `+0x11f8` | `(.8, 2.7, 10, .01)` | `1.1933 / 2.7000 / 5.5797` | `1.19 / 2.70 / 5.58` |
| Impedance Cutoff | `+0x1148` | `(.3, 1, 3, .01)` | `.4821 / 1.0000 / 1.8414` | `.48 / 1.00 / 1.84` |
| Impedance Slope (`q_factor`) | `+0x11a0` | `(.2, 1, 10, .01)` | `.2671 / 1.0000 / 3.6607` | `.27 / 1.00 / 3.66` |

全部 15 个点均落在显示精度的半格 `0.005` 内，最大绝对差 `0.003717`。计算采用 API 读回的实际归一化浮点值，而非只使用理想 `0.25/0.5/0.75`。原始测量在 `audio-pass2/parameters/measurements.json`，逐点预测在 `mapping-formula-validation.json`。

这些曲线关联同时得到属性查找 switch 的静态证据和公开接口采样的动态证据。已证明元数据索引到标度对象的路径；仍未找到从求值结果到最终物理模型系数的全部 setter 路径。

Forte 使用不同的三节点构造器，确认节点为 `(0,0)`、`(.5,1.6)`、`(1,2)`；实测 `.25/.5/.75` 显示 `.80/1.60/1.80`，与分段线性相符。随后取得的节点求值核心确认按区间插值，普通分支为线性横坐标，另有对数横坐标分支；具体标志位限制见文末。Impedance 也使用节点映射，本节没有将幂公式套到它上面。

**音频验证与上述验证分开。** 参数读回成功并不能证明离线渲染载入了更新的状态。初轮 A/B 曾产生相同 WAV，正在由音频实验单独调查预设保存/回调提交链路；本节不将其报告为音色响应成功。

## 元数据到标度记录桥接的复核边界

进一步读取 `FUN_100933408` 确认其只是管理对象中各标量属性的零值/默认值初始化，没有写入元数据索引对应表。全局对象的两处候选引用（`pass2-registry-get-a/b.json`）实际落在同一个 `FUN_100623a58`：它从 12 字节参数引用中的 `ushort` 成分取 ID，查 `metadata_begin+ID×0x88`，检验 `record.ID==ID`，再拼接名称。这里确认了元数据 ID 的使用方式，但没有访问对应 `0x58` 标量属性记录。

`FUN_1006d9b10` 处理某类首 ID 为 `0x96` 的引用重写；`FUN_1006da114` 检测 `FUN_1001c0c70` 返回值。这些包装本身不是 setter，但由其调用继续追踪 `FUN_1001c0c70` 后，确实找到了下面的属性桥接。

三节点映射构造 `FUN_10016d8cc` 设虚表 `0x100b7d538`，检查首末归一化节点为 0/1，验证节点顺序和单调性，并建立交换横纵坐标的反向表。其正向方法 `FUN_10032c250` 委托给 `FUN_100019a34`，模式 2。继续追入该包装的下级求值核心，结果见文末；不能根据包装本身宣称具体插值形式。

这轮静态复核没有启动音频宿主，也没有修改 Pianoteq 或 Just Piano。

### 节点求值核心的明确公式与条件

最新 `FUN_10044f8a4` 已提供节点求值核心，而非只有函数结构。对输入 `x`，函数找到包围节点 `(xi, yi)`、`(xj, yj)`，输出：

```text
y = (1 − t) × yi + t × yj
```

当数据对象 `+0x4c` 的 bit 0 为 0 时，`t=(x−xi)/(xj−xi)`；区间宽度不大于 `10⁻³⁰` 时使用 `t=1`。当该 bit 为 1 时，横坐标先夹到 `[10⁻¹⁰,10¹⁰]`，再用 `t=ln(x/xi)/ln(xj/xi)`。对象 `+0x4d` 为 1 时会转入另一个求值器，不能将该路径省略。模式 2（来自正向包装）在节点区间外选择首/末区间继续插值；模式 3 有边界钳制行为。

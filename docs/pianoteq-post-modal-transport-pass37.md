# pass37：计算的模态组接到输出块传输

本轮继续追踪 pass36 的完整模态组输出。已将自己的组样本接到原生块间传输和后处理旁路，四个场景各 11520 个 float32 检查逐位同，共 **46080 项**。这验证了渲染后的一个真实输出环节，尚未得到最终麦克风/立体声混合或完整网页音源。

## 从实际运行栈定位消费者

单固定硬件点取得的运行栈为：

```
7c0bcc modal kernel
  ← 4e285c group renderer
  ← 472f20 controls/render/post-processor
  ← 20b28c voice group handling
  ← 4165d8 worker dispatch
```

REA 的静态 callers 返回另一个已解析直接调用者；它不能列出此处所有虚表调用。运行栈与 `4e285c` 中的间接调用一起确定了本次实际路径，不是仅凭函数名推断。

[pianoteq_capture_post_modal.py](../scripts/pianoteq_capture_post_modal.py) 在 `472f64`（模态渲染后、后处理前）、`472f70`（后处理后）、`20b418`（声部组处理后）使用三个固定硬件点读取真实矩阵。三个内部组不能当作左右声道。

## 54 的存储值为什么只延迟 52 个样本

直接拿 pass36 同 counter 或相差一块的缓冲比较，都出现 2880/2880 不同，原诊断保留。后续读到 V+76c=54、V+768=64，并核对原指令：

```
copyVectorCount = V76c >> 2
effectiveDelaySamples = 4 * copyVectorCount
```

因此实际搬运延迟为 52，不能直接使用 54，也不能将它忽略。每组输出先取得前一模态块末尾 52 个样本，再接当前模态块前 12 个样本。当前块余下 52 个样本成为下一块的历史。

此外 `4e285c` 返回前已将 V+10 加上块长。所以后处理捕获的 counter=3328 对应 pass36 模态块 counter=3264；这是一处原生计数器更新，不是拟合出的任意音频对齐偏移。

[post-modal-transport.mjs](../dsp/post-modal-transport.mjs) 保留上述整数取整和历史传递。[重放器](../scripts/pianoteq_replay_post_modal.mjs) 只读取一次前导历史尾部，其后所有当前模态块来自 pass36 已计算的完整组缓冲，原生 rawModal 仅作为比较目标，不逐块注入。

## 实际结果

| 场景 | 已计算模态源 | 15 块检查 | 调试捕获的原生 PCM |
|---|---|---:|---|
| 无踏板 | pass36 同进程释放计算报告 | 11520/11520 | 原版短音基准同 |
| CC64=64 后抬起 | pass36 半踏板计算报告 | 11520/11520 | 对应原版刺激同 |
| CC64=96 后抬起 | pass36 worker 计算报告 | 11520/11520 | 对应原版刺激同 |
| Stereo Width 接口 .25 | 相同无踏板计算报告 | 11520/11520 | 该修改预设的原版渲染同 |

每场景检查 2880 个 raw 模态组值、2880 个传输后值、2880 个后处理后值和2880 个声部组处理后值。源报告来自不同原生运行，报告明确 `modalBlocksFromSeparateVerifiedRun=true`。本轮没有将跨运行对照表述成新的同进程声部递推。

窗口仍约 20ms，前导 counter=3264 用于历史初始化，计算源覆盖 counter=3264..4160，对应后续输出 counter=3328..4224。没有完整 JavaScript 钢琴 WAV，也没有最终立体声等价性结果。

## 后处理与组混合的验证边界

本次 V+840 处理器的当前/目标混合值都为 0，enabled bit0 为 0，`92d304` 确实立即返回。重放器要求这一旁路条件，否则拒绝；没有用旁路样本声称已验证活动滤波/混合路径。

`20b28c` 中 H+128 小于 1 时，静态指令给出：

```
for group = 1..N-1:
    group0[i] = fma32(f32(1-factor), group[i], group0[i])
    group[i] = f32(factor * group[i])
```

已写出该算术，但本批实际 factor 都为 1，所以非单位分支尚未动态验证。它是一个内部组混合量，不能因为形式类似宽度控制就命名为 GUI Stereo Width。

## Stereo Width 保存与负关联实验

首次 headless、音频 stopped 的实验中，接口显示 `stereo_width=.25`，保存后全新进程却恢复为 .5，失败保留。随后在自己创建的 `--no-prefs` 临时官方实例中，通过 Devices 选择系统默认输出，确认状态 running，设置 .25、等待提交并保存。新进程读回 215 项全部吻合，接口仅 Stereo Width 这一项改变，显示值为 0.20。

实际修改预设的 H+128 仍为 1，四段内部组输出也都与原无踏板计算一致。本次修改不能证明 GUI Stereo Width 通过 H+128 起作用。其完整原版 WAV 与旧干声基准不同，帧数从 113152 变为 116992；公共长度内首差在第980帧。后续应在同一保存流程中补足基准对照，再定位此后混合路径，避免将保存/序列化变化误当成唯一参数因果关系。

所有实验实例均已正常请求 quit，监听端口关闭。只修改临时实例与新建分析预设，没有修改原程序或授权状态。

## 保留的失败与完整性检查

一次新增捕获启动后停留在 getcwd→open 系统调用，尚未输出 WAV。保存了程序与 LLDB 的真实采样栈；向调试器发送中断未结束等待，随后终止该实验子进程，确认终态后才用独立新目录重试。将子进程工作目录换到本机私有研究目录后正常完成；没有修改 macOS 权限，也未证明系统调用等待的唯一根因。

一次只按相同 `0x4cc` 偏移搜索到的函数实际是颜色表初始化，已作为错误对象匹配拒绝，不能用它解释模型字段写入。这份失败静态线索保留，未据此建立参数映射。

将一个 rawModal 比较值改一 ULP，只产生一处失败，传输预测仍使用自己的源块；修改一个传输后的比较值，同样只失败一项；删除一个阶段则被结构检查拒绝。三个负对照都 exit 1。完整审计另外核对原生退出状态和真实 WAV，启动中止记录明确失败。

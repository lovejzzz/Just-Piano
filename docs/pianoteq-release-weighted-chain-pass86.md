# 释放与再击控制到指数权重及实际模态幅度：pass86

本轮把自己的对数谱继续送入指数与模态加权，在同次运行中比较真实权重和加权后四张表。新模块参与计算，但预加权源表仍观察，尚非完整独立声源或声音复刻。

## 九点尝试明确失败

pass78只测试过六个硬件站点，不能据此称六点就是硬件上限。本轮在独立自建探针中先测试七点、再测试九点：均明确显示hardware、各命中一次并正常exit0。该证据只适用于探针。

试图在Pianoteq同次保留初始化、动态更新、对数谱、指数与加权等九个点时，A进程3922在任何点命中之前报告cannot run / Please reinstall并exit1。九点命中数均0，窗口complete=false，之后关闭点并退出LLDB。保留九点源码与日志，不将探针成功当Pianoteq成功，不认定拒绝原因，也不修改安装、完整性或授权检查。

随后使用正常六点配置继续数值调查，没有更改应用二进制/数据/PC或寄存器。为覆盖权重前后，本轮省去初始化与对数谱站点；其源模型字段和时间步重新作为观察输入。**不能因此宣称已把pass85的源初始化和本轮加权同时闭合。**

## 负对照与实际传播

47项负对照均先要求基准exit0，再拒绝篡改/缺失事件。高档Rattle源设为0会改变加权前34个指数值、加权后相同34个指数值及**102个实际幅度值**；u扰动也传到相同数量的权重/幅度。基础谱源和附加源表扰动分别产生130/156差异。改变一个原生权重或加权目标只产生1处差异，表明这些目标没有进入自己的后续计算。缺失配对、错误模式/所有者/维度和counter均拒绝。

并非所有局部源变化都影响本窗口终端；例如仅扰动首次系数模型的试验未传到加权结果，保留其有限敏感性。没有把负对照当成新增原生分支覆盖。

## 普通Continue与停止证据

C的自动守卫先拒绝一种trace停止：工作线程在包络返回站点+4，另一线程停在自有copy站点。核对最后回调的地址/命中数、声部epoch、实时counter和position后，只更新宿主Continue辅助函数，允许这种精确形态且仍要求另一线程命中自有站点。8项模拟守卫检查包含实际形态一次Continue，以及错误PC/旧命中/错误声部/计数/位置/意外IDs/无自有站点七种拒绝。

稍后在libsystem_kernel的__psynch_cvsignal+8又停一次，自动守卫拒绝且未加入内核地址白名单。保存现场栈（pthread_cond_signal→condition_variable::notify_one→已有声部调度函数），检查线程计划后，人工工具执行一次普通debugger continue；全部观察点保持启用，又采到2个包络块，最后原生exit0才finish。没有跳转PC、改写寄存器/数据/代码、删除系统检查或注入目标调用；两次自动拒绝和普通Continue均保留在日志中。停止原因本身仍未查明。

## 实际音频连长度也不相同

正常官方CLI、同FXP/MIDI和--multicore 0，原版参考与C均exit0、双声道24-bit/48kHz。但C为**143360帧**，原版参考**148224帧**，完整格式/PCM检查直接失败，没有截取共同前缀或放宽容差。C PCM SHA256为369eb1bbbbd5c46b86dfa4a0d11d12ec5532e9c7ed4825c08e438ec388c321e9。

这仍是原生WAV，不是该JS模块独立生成的完整音频。局部控制/谱/幅度一致没有解决调度与尾部差异，也没有证明声音完全一致。
